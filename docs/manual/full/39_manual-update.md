# 第39章 マニュアル更新手順

## 39.1 原本と配置を確認する

**`docs/manual/`配下のMarkdownが編集原本**である。生成したPDFは印刷・配布用の出力であり、正本として直接修正しない。PDFで誤りを見つけたらMarkdownまたは共通画像を直し、PDFを再生成する。全体の構成は[マニュアル原本README](../README.md)を参照する。

| 場所 | 更新するもの |
| --- | --- |
| [`full/`](./) | 詳細版。画面操作、業務上の確定条件、連携の境界、障害時の確認先を記す |
| [`quick/`](../quick/) | 簡易版。日常操作の手順と判断に必要な注意を短く記す。内部実装の詳細は詳細版へ寄せる |
| [`assets/screenshots/`](../assets/screenshots/) | 両版で共用する実画面の画像。章ごとに同じ画面を複製しない |
| [`assets/diagrams/`](../assets/diagrams/) | データの流れや状態の境界を表す図解原本・画像 |
| [`previews/`](../previews/) | A4印刷時のページ構成、文字量、画像の可読性を確認するレイアウト見本 |

`previews/`や生成PDFを更新しても、対応する章の記述が古ければ更新完了ではない。

## 39.2 変更の種類から更新先を決める

| アプリ・業務の変更 | 確認して更新する場所 |
| --- | --- |
| UIの文言・配置・入力・操作順が変わった | 対象の詳細版と簡易版の手順、該当する共通スクリーンショット、画像中の番号・矢印。印刷時の見え方が変われば該当preview |
| 状態遷移・確定条件・保存先・連携ロジックが変わった | 対象の詳細章と図解。日常の判断・操作に影響する場合は簡易章も更新し、該当previewの説明と流れを確認 |
| 業務フローや章構成が変わった | 詳細版・簡易版の関係する章、各目次、READMEの章案内、関連するpreview。新しい章への参照も確認 |
| 画像や文章の差し替えだけでページの長さ・配置が変わった | 対象previewを更新し、A4で文字と画像が読めるか確認 |

変更した画面だけを見て終わらせず、「受付から納品まで」の前後手順と、同じ画面を参照する両版の章を確認する。逆に、変更のない画像・図解を機械的に撮り直さない。

## 39.3 現行実装とproductionを照合する

記載前に対象の画面・API・処理と[ステータスの正本](35_status-source-of-truth.md)を確認し、Task記録・現在のproduction source commit・deployment・smoke結果と照合する。local実装、commit、production反映、外部連携の実動作は別段階である。確認できた段階だけを「できること」として記し、未実装・未検証・結果不明はそのまま明示する。[第38章](38_backup-migration-deploy.md)のproduction記録も参照する。

Task202Bの公式配送status code説明表示はproduction完了済みとして扱う。一方、Task204の実引受に基づく発送更新、追跡番号保存、LINE発送通知、配達完了からRepair納品済みへの自動連携と、raw日付値のparse・timestamp保存は未実装である。現行のゆうプリR発送履歴はread-only previewであり、候補値をShipmentへ保存しない。[第25章](25_yupuri.md)と[第35章](35_status-source-of-truth.md)を照合する。ロードマップの予定と現行操作を同じ手順に混ぜず、予定が必要なら「未実装」と分けて書く。

## 39.4 画面画像を安全に更新する

- 実アプリUIまたは確認済みの現行UI構造に、合成した非顧客データを表示して撮影する。実顧客の氏名、住所、電話番号、LINE会話、時計写真、案件番号などの個人・業務情報を載せない。
- 撮影前と保存後に画面全体を確認し、API token、cookie、認証header、secret、接続文字列、署名付きURL、QR payloadなどの機密値が写っていないことを確かめる。ブラウザのアドレスバーや開発者ツールも確認対象にする。
- 必要部分を読める大きさで切り出し、操作番号・囲み・矢印が現行UIの位置と一致するか確認する。共通画像を差し替えたら詳細版・簡易版の双方で表示を確認する。

## 39.5 目次と参照を揃える

1. 詳細版の[目次](00_toc.md)と簡易版の[目次](../quick/00_toc.md)で、章番号・章名・実ファイル名を照合する。READMEの章案内も対象章に合わせる。
2. `full/`と`quick/`の章ファイルを一覧にし、欠番と重複番号を確認する。欠番を見つけても架空の章を作らず、現行の目次と実ファイルの差として記録する。
3. 追加・改名・移動した章からの相対リンク、関連章からその章への逆参照、画像・図解・previewへの参照先を確認する。リンク先の存在に加え、参照文が現行内容を正しく表すか読む。

## 39.6 印刷版を発行する

1. **監査:** 現行実装・productionとの整合、未実装表示、目次・リンク、画像の安全性、詳細版と簡易版の齟齬を確認する。
2. **組版:** Markdown原本と共通画像から詳細版と簡易版をそれぞれ組み立て、`previews/`でページ構成・画像サイズ・文字量を確認する。
3. **最終調整:** 内容とページ順が固まってから、通しページ番号とヘッダー・フッターを付ける。章の追加・移動後は番号を振り直す。
4. **出力・検品:** A4カラーPDFを生成し、**全ページ**を目視で確認する。さらに全ページの本文・見出し・ページ番号を文字として確認し、欠落、文字化け、リンク切れ、図の潰れ、ページ送りの乱れを直す。

組版・PDF生成に使う実際のツールとコマンドは作業環境ごとに確認する。共通手順が定まるまでは特定のコマンドを前提にしない。修正後は両版を再出力し、該当ページだけでなく全ページを再検品する。

## 39.7 docs-onlyの差分と境界を守る

- 作業前と提出前に`git status`で既存差分を確認する。**1 Task = 1 commit**の単位で対象文書だけを扱い、Task外の未追跡・未commitファイルをstage・削除・変更しない。`git diff --check`で空白やpatchの不備を確認する。
- docs-only Taskはproduction deployを伴わない例外として**`Production: pending`**と記録する。このprojectではpushはユーザー確認後に行う。commit・push・deployを同じ完了条件として扱わない。
- 文書調査でschema／migration、RLS／GRANT、auth、決済、production DB、LINE実送信などの変更が必要と分かっても、このマニュアル更新Taskでは実施しない。別Taskで実装・独立review・必要な承認を受ける。[第38章](38_backup-migration-deploy.md)を参照する。
