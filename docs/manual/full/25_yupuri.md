# 第25章 ゆうプリクラウド発行とゆうプリR CSV

## 25.1 現在使える範囲

通常運用では、`/shipments` で人が `ゆうプリクラウド発行を依頼` し、Windows WorkerがCSV登録、発行、追跡番号取得、PDF取得、`NEC MultiWriter 5750C` への印刷を進める。発行依頼でShipmentがREADYになり、配達希望の通常変更はロックされる。Workerの自動操作時間は日本時間06:00以上23:55未満。専用Edgeのログイン画面が出た場合は人が復旧する。結果不明時は盲目的に再発行しない。

ゆうプリR標準フォーマットV3 CSV出力と発送履歴previewは代替・照合経路として残る。`/shipments` にV3出力ボタンはない。送り状の発行結果・紙・郵便局への引渡しは現物と外部側で確認する。

ゆうプリRの両APIは管理者認証が必要である。API利用環境が整っていない担当者は、管理責任者に運用方法を確認する。

## 25.2 V3 CSV出力

出力先は `GET /api/shipments/[id]/yupuri-v3`。`[id]` は対象Shipment IDに置き換える。出力できるのは **OUTBOUND・`actualShippedAt = null`・statusが `DRAFT / READY / LABEL_ISSUED / AWAITING_ACCEPTANCE` のいずれか** のShipmentだけで、それ以外は拒否される。宛先はShipment作成時のdestination snapshotを使い、顧客マスタの現住所には戻らない。配達希望日・時間帯を出力用コードへ変換できない場合や文字コードで表現できない文字がある場合は、推測せず出力を拒否する。

| CSV仕様 | 現行値 |
| --- | --- |
| 形式 | ゆうプリR 標準フォーマットV3、100列、headerなし |
| 文字コード | CP932 / Shift_JIS、BOMなし |
| 改行 | CRLF |
| お客様側管理番号 | `SHP-{Shipment.id}` |
| 内容品 | 腕時計 |
| 荷物サイズコード | 現時点では `060` 固定 |

実際の荷物が60サイズ以外になる場合、この固定値を流用しない。荷物サイズをShipment側で管理する後続設計が必要である。CSV取得だけではShipment、Repair、追跡番号、status、送り状発行日時は変わらない。

## 25.3 発送履歴CSVの読取プレビュー

`POST /api/shipments/yupuri-history/preview` は、ゆうプリRの発送履歴CSVを読んで照合候補とエラーを返す管理者用API。現行の取込契約はCP932、BOMなし、CRLF、headerあり6列、1ファイル256 KiB・データ500行まで。`SHP-{id}` 形式のお客様側管理番号でShipment候補を探し、お問い合わせ番号、引受関連日、配達完了日、集約・明細status codeを **候補・raw値** として表示する。

Task202Bで、日本郵便の公式表に記載された集約・明細status codeの組と説明をpreviewへ追加した。たとえば`10/0A = 引受予定`、`11/01 = 引受`、`52/01 = 配達完了`を公式表記として表示する。`10/0A`は実引受を示さない。公式表で説明が「-」の組は説明なし、表にない組は未確認として警告する。重複管理番号、照合不能、追跡番号の競合、形式不正はエラー扱いとする。

プレビューは **読取専用**。追跡番号、Shipment / Repair status、実発送日時、配達完了日時を書き戻さない。`importableLater` はエラーなし・Shipment照合済み・公式説明ありの将来取込候補を示すだけで、状態判定や書込承認ではない。14バイトの日付値はraw文字列のまま返し、日時としてparse・保存しない。非空日付値の実CSVが不足しているため、書式・タイムゾーンを推測しない。履歴取込の共通画面はなく、APIで確認しただけでは配送状態は更新されない。

## 25.4 発送後の現在地

ゆうプリクラウド発行時の追跡番号保存は運用中。一方、発行後CSVによる引受・配送状態同期、LINE発送通知、Repair納品済み反映は実装・deploy済みでも、2026-10-13時点で永続同期OFF・実発送E2E前。CSV出力、発行、履歴previewだけで「発送済み」「配達済み」と判断しない。現行確認手順は[第26章](26_shipping-tracking-delivery.md)を参照する。
