# 第11章 部品検索・発注・部品待ち

## 11.1 部品行と発注は別工程

見積へ交換部品を追加することと、実際に部品を発注することは同じではない。

アプリでは次を分離している。

```text
見積の交換部品行
  ↓ 必要部品を特定
PartsMasterへ紐付け
  ↓ 不足確認
OrderRequest
  ↓
pending → ordered → received → assigned
```

見積編集中に部品を選んだだけで、承認前案件の在庫を勝手に引き当てない。

## 11.2 PartNameMasterとPartsMaster

部品関係では、名称マスタと実部品マスタを混同しない。

### PartNameMaster

標準化した部品名を表す。

例として「どの種類の部品か」を構造化入力するために使う。

### PartsMaster

実際の調達・在庫対象となる部品を表す。

主な情報:

- 日本語 / 英語名
- 部品Ref
- Cousins番号
- グレード
- 在庫数量
- 仕入価格
- 仕入先
- 対応する時計 / Cal等の条件

交換部品行はPartsMasterへ紐付けられる。

## 11.3 部品検索

見積の交換部品行にある検索ボタンから部品パネルを開く。

候補を選ぶ際は、案件に応じて次の条件を確認する。

### 内装部品

- movementメーカー
- movement Cal
- base movement
- 標準部品名

### 外装部品

- ブランド
- モデル

一致しない候補を「近そう」という理由だけで登録しない。

## 11.5 承認前の先行発注

業務上、顧客承認前でも「承認される可能性が高く、先に部品を確保したい」ケースがある。

現在は、ヨシダ側の明示操作で不足部品のOrderRequestを承認前に作成できる。

ただし、**承認前の先行発注と、案件への在庫引当は別処理**である。

承認前にOrderRequestを作っても、次は行わない。

- RepairPartAllocationの作成・更新
- PartsMaster.stockQuantityの案件用減算
- Repair.statusを部品待ちへ自動進行
- approvalStatusの変更

見積へ部品を追加しただけで全案件を自動先行発注するわけでもない。発注が必要な部品を明示的に選んだ場合だけ発注依頼を作る。

## 11.6 OrderRequestの状態

発注管理では主に次の状態を使う。

| 内部status | 画面表示 | 意味 |
| --- | --- | --- |
| `pending` | 発注リスト追加済み | 発注候補として登録済み |
| `ordered` | 注文済み | 仕入先へ注文済み |
| `received` | 入荷済み | 工房へ物理的に入荷済み |
| `assigned` | 案件へ割当済み | Repair用部品として確保済み |

`received` と `assigned` は異なる。

入荷済みになった時点では一般在庫へ入っただけで、特定Repairへ確保済みとは限らない。

## 11.8 pending → ordered

実際に仕入先へ注文したら「発注済みにする」を押す。

初回のordered遷移で `orderedAt` を保存する。

承認前に先行発注している場合でも、pending → orderedは可能である。この時点では案件在庫引当を行わない。

## 11.9 入荷予定日

発注時の入荷予定日は、設定が揃っている場合に次から算出する。

```text
orderedAtの日本時間暦日
+ Supplierの手動処理日数
+ 調達配送方法の手動輸送日数
= expectedArrivalDate
```

処理日数または輸送日数等が不足している場合は `未算出` になる。

Supplier設定や配送方法設定を後から変更しても、既存発注の保存済み予定日を一括で勝手に変更しない。

## 11.10 ordered → received

部品が工房へ物理的に届いたら「入荷済みにする」を押す。

この遷移では `receivedAt` を実入荷日時の正本として保存する。

入荷は物理在庫イベントなので、承認前でも実際に届いた部品はPartsMasterの在庫へ加算される。

ただし承認前B2C Repairへ自動的に割り当てない。

## 11.11 received → assigned

入荷済み部品を対象Repairへ確保するときに「案件へ割当」を使う。

B2Cでは顧客承認前の案件への割当を禁止している。

承認前にreceivedまで進んでいても、`assigned` は顧客承認後に行う。

割当時は現在の必要数量・既存割当・在庫を再確認し、在庫不足や状態変化があれば安全側で停止する。

## 11.12 発注数量の二重加算を防ぐ

pendingのquantityは「今回ボタンを押した分を毎回足す値」ではなく、現在不足している数量の目標として扱う。

概念的には次を考慮する。

```text
必要数量
- 案件へ割当済み数量
- 利用可能な在庫
- 注文済み数量
= 追加で必要なpending数量
```

同じ操作の再送やRepair再保存によってpending数量を二重加算しない。

既にordered / receivedへ進んだ数量も考慮し、同じ部品を重複発注しないようにする。

## 11.13 承認後の部品status

顧客承認後は、activeなOrderRequestをもとにRepairの部品工程を同期する。

- pendingあり → `部品待ち(未注文)`
- orderedあり → `部品待ち(注文済み)`
- 必要なactive orderがreceived段階 → `部品入荷済み`
- 必要部品が案件へ確保され、activeな部品待ちがなくなる → `作業待ち`

複数OrderRequestがある場合、未処理のものを含めて案件全体で判断する。

## 11.14 部品準備日

Scheduler用の部品準備判定では、単に「荷物が届いた」だけをREADYとしない。

主な判定:

- `NOT_REQUIRED` — 必要部品なし
- `READY` — 必要部品が案件へ全量確保済み
- `WAITING` / `WAITING_UNKNOWN` — 不足部品待ち
- `LEGACY_UNKNOWN` — 旧データで信頼できる引当台帳がない

orderedのexpectedArrivalDateやreceivedAtから、全不足部品が揃う見込み日 `partsReadyDate` を導出できる場合がある。

`partsReadyDate` は保存済み固定日ではなく、現在の発注・割当状態から導出する。

## 11.15 部品待ち中断

RepairPlanningStateで `WAITING_PARTS` を理由に作業中断を記録できる。

部品準備見込み日がある場合はresumeEligibleDateの入力候補として利用できるが、自動resumeはしない。

部品が届いたことと、作業を再開する判断も分離している。
