# 第12章 見積り待ち / 見積り調査中 / 承認待ちの運用

## 12.1 「案件status」と「現物の置き場所」を分けて考える

見積工程では、似た日本語が複数の場所で使われるため注意する。

現在のRepair.statusとして存在する代表的な状態:

- `受付`
- `見積中`
- `承認待ち`
- `保留`

一方、StorageLocationには次の物理ゾーンがある。

- 見積り待ち
- 見積り調査中
- 承認待ち

**「見積り調査中」は現在、独立したRepair.statusではない。**

見積が長引く時計を物理的に分離するためのStorageLocationとして利用できるが、Repairの業務statusは現在 `見積中` を維持する。

## 12.2 受付処理後

現物受付・PhysicalTag・StorageLocation登録が完了したら、時計を見積工程へ進める。

通常は次のように考える。

```text
Repair.status = 受付
StorageLocation = 受付処理待ち
  ↓
見積作業を開始
  ↓
Repair.status = 見積中
StorageLocation = 見積り待ち または 見積り調査中
```

status変更だけで現物のStorageLocationを自動変更しない。

## 12.3 見積り待ち

通常の見積作業を待つ時計は `見積り待ち` ゾーンへ置く。

Repair.statusが `見積中` の場合、現在のStorageLocation推奨ロジックは `見積り待ち` をrecommendedとする。

## 12.4 見積り調査中

すぐに金額や修理可否を判断できない案件は、物理的に `見積り調査中` へ分離できる。

例:

- 部品供給可否の確認が必要
- 代替部品調査が必要
- 加工 / 製作方法の検討が必要
- 外注先へ確認が必要
- 現物をさらに調査する必要がある

現在のStorageLocation推奨ロジックでは、Repair.statusが `見積中` のとき `見積り待ち` と `見積り調査中` の両方を許容する。

そのため、調査中の時計を物理的に別箱へ移しても「不一致」にはしない。

## 12.5 現時点で未実装の調査管理

ロードマップでは将来、見積り調査中について次を追跡する方向としている。

- 調査開始日
- 次回確認日
- 継続理由
- 一定日数経過時の注意表示
- 調査継続 / 顧客へ途中連絡 / 見積困難として返却の判断促進

ただし、これらを独立したRepair状態として保存する仕組みは現時点のproduction完成機能ではない。

マニュアルでは、将来予定を現在の操作として扱わない。

## 12.6 見積書完成から承認待ちまで

見積明細が完成した後の正規フロー:

```text
Repair = 見積中
  ↓
Repair一覧で対象を選択
  ↓
見積書作成
  ↓
保存済みPDFを生成
  ↓
PDFを開いて人が確認
  ↓
LINEで送信
  ↓ Outbox APPROVED
ローカルsender
  ↓
LINE Manager実送信・履歴照合
  ↓ CONFIRMED
Repair = 承認待ち
approvalStatus = pending
```

見積書作成やOutbox登録だけを理由に、手動で先に `承認待ち` へ進める必要はない。

## 12.7 承認待ち

`承認待ち` では、顧客共有ページからの回答を待つ。

B2C顧客は次を行える。

- 見積内容を見る
- PDFを見る
- 返送先を確認・修正する
- 「この内容で進める」で承認する
- 「LINEで相談する」から内容変更等を相談する

B2C共有ページには現在、直接の「差戻し」ボタンやインライン修正依頼ボタンは表示していない。

物理時計は通常 `承認待ち` StorageLocationへ移す。

## 12.8 承認された場合

顧客が承認すると `approvalStatus = approved` とapprovalDateを保存し、部品状態を再計算する。

その結果、次のどれかへ進む。

```text
承認済み
├─ 不足部品なし / 準備済み → 作業待ち
├─ 未注文不足あり           → 部品待ち(未注文)
├─ 注文済み                → 部品待ち(注文済み)
└─ 入荷済み・割当待ち       → 部品入荷済み
```

StorageLocationも実際の現物移動に合わせて変更する。

## 12.9 修正・相談が返ってきた場合

B2Cでは、顧客が共有ページの「LINEで相談する」から内容変更を相談する。相談内容を確認し、必要なら見積明細を修正する。

B2C共有ページには現在、見積を直接 `rejected` にする差戻しボタンは表示していない。

B2B共有ページの「修正を依頼する」では、理由を保存したうえでRepairを `保留`、approvalStatusを `rejected` とする処理がある。B2B固有のこの回答UIをB2Cの日常操作と混同しない。

見積を修正する場合の基本手順:

1. 顧客の相談内容を確認する。
2. 必要なら見積明細を修正する。
3. Repairの業務statusを適切な見積工程へ戻す。
4. 保存済みPDFを再生成する。
5. PDFを確認する。
6. 新しい内容をLINEで再案内する。

古い共有内容をそのまま承認させないよう、最新版を確認してから再送する。

## 12.10 見積不要・事前承認の将来方針

ロードマップでは、次のような案件を単純なbooleanだけで扱わない方向としている。

- 料金確定済み
- 上限金額まで事前承認済み
- 見積提示を省略できる定型案件

上限以内なら承認待ちを省略し、上限超過時だけ再承認へ戻す等の設計を予定している。

ただし、これは本章作成時点で完成済みの一般操作フローとしては扱わない。

電池交換等の作業種別だけを理由に「自動で見積不要」と判断しない。

## 12.11 現場で迷ったときの判断表

| 状況 | Repair.statusの考え方 | StorageLocationの例 |
| --- | --- | --- |
| 現物受領直後 | 受付 | 受付処理待ち |
| 通常の見積待ち / 作成中 | 見積中 | 見積り待ち |
| 難しい調査が長引いている | 見積中 | 見積り調査中 |
| 見積を実送信確認済み | 承認待ち | 承認待ち |
| B2C顧客からLINE相談 | 状態は自動変更しない。内容確認後に管理側で判断 | 現在地を維持、必要なら要確認 |
| 承認済みで部品不足 | 部品待ち系 | 部品待ち |
| 承認済みで作業可能 | 作業待ち | 作業待ち |

## 12.12 自動化しすぎない理由

見積・承認・部品調達では「実際に顧客へ届いたか」「本当にこの部品か」「現物をどこへ移したか」等、人間確認が必要な境界が多い。

そのため現在のアプリは、次のイベントを分離している。

- Repair保存
- 見積書作成
- PDF生成
- LINE送信intent登録
- LINE実送信確認
- 顧客承認
- 部品発注
- 部品入荷
- Repairへの部品割当
- 現物保管場所移動

1つのボタンで全てを不可逆に進めるのではなく、各境界で正本データを確認して次へ進める設計である。
