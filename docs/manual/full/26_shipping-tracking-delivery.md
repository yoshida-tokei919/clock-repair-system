# 第26章 発送・追跡・配達完了 — 現行運用と制限

> **この章の前提:** Task202Bの公式配送status codeの説明表示はproduction完了済み。Task204の実引受に基づく発送更新、追跡番号保存、LINE発送通知、配達完了からRepair納品済みへの自動連携は未実装である。本章は現在の実装で発送後を安全に扱うための確認手順を示す。

## 26.1 この章の範囲

第22〜25章でShipment作成、梱包照合、PhysicalTag release、ゆうプリR向けCSV出力と発送履歴CSVのread-only previewまでを説明した。本章では、その後の「送り状発行」「現物引渡し」「追跡」「配達完了」を、現行アプリで自動確定できる範囲と外部で確認する範囲に分ける。

現行アプリは、配送会社へ直接追跡照会を行うAPI連携を持たない。ゆうプリRの発送履歴CSVを読めても、その結果をShipmentやRepairへ自動保存しない。

## 26.2 現時点でできること / できないこと

| 工程 | 現在の確認場所・正本 | 現行アプリの動作 |
| --- | --- | --- |
| ゆうプリR向けデータ作成 | Shipmentの宛先snapshot・配達希望 | V3 CSVを生成できる |
| 送り状発行・印刷 | ゆうプリR側・実際の印刷物 | CSV生成だけでは発行済みにしない |
| 荷物の実引渡し | 現物、受付控え、日本郵便側の実績 | 自動で`actualShippedAt`を保存しない |
| 追跡番号 | 送り状・ゆうプリR・日本郵便側の番号 | 発送履歴previewでは候補/raw値として読むだけで自動保存しない |
| 実引受 | 日本郵便側で実際に引受済みと確認できる事実 | `10/0A = 引受予定`を実引受として扱わない |
| 配達完了 | 日本郵便の実追跡結果 | previewだけで`deliveredAt`やShipment / Repair statusを書き戻さない |
| LINE発送通知 | 後続Taskの対象 | 自動送信しない |
| Repair納品済み連携 | 後続Taskの対象 | 配達完了から自動更新しない |

## 26.3 発送前に確認する

発送後の追跡以前に、次を完了しているか確認する。

1. Shipmentの対象Repairと返送先snapshotが正しい。
2. 配達希望の反映状態を確認した。
3. PhysicalTagの梱包照合が全件一致している。
4. 再利用するPhysicalTagのactive割当を、現物確認後にreleaseした。
5. ゆうプリRへ渡すCSVの対象Shipmentと宛先を確認した。

梱包照合やPhysicalTag releaseは、実発送を意味しない。Shipmentのstatus名だけで配送会社が荷物を受け取ったと判断しない。

## 26.4 送り状発行と現物引渡し

V3 CSVをゆうプリRへ取り込み、ゆうプリR側で送り状を発行・印刷する。印字された宛先、配達希望、サービス、荷物と対象Shipmentを現物で照合する。

その後、集荷または郵便局への持込等、実際の方法で荷物を日本郵便へ渡す。

**CSVを出力した時点、送り状を印刷した時点、Shipmentを作成した時点のいずれも、実引受の証拠ではない。** 実際の引渡しと配送会社側の事実を分けて確認する。

現行UIにない項目を埋めるためにproduction DBを直接編集しない。追跡番号や実発送日時等の書戻しは、対応する実装と検証が完了するまで後続Taskの範囲とする。

## 26.5 発送履歴CSVを確認するとき

発送履歴CSVを入手できる場合は、第25章のread-only previewでShipment候補、raw値、公式表に説明があるcode pairの表記を確認できる。

preview結果を見るときは次を守る。

- `SHP-{Shipment.id}`のお客様側管理番号が対象Shipmentと一致するか確認する。
- 追跡番号候補と14バイトの日付値は**候補/raw値**として読む。日付値のparse・timestamp保存は未実装である。
- 公式表で説明があるcode pairはその表記を表示する。「-」の組は説明なし、表にない組は未確認の警告となる。
- 重複管理番号、照合不能、追跡番号競合、未確認codeがあれば推測で解決しない。
- `10/0A = 引受予定`は実際の郵便局引受を示さない。
- `importableLater`は将来の取込候補であり、Shipment状態の判定や更新承認ではない。
- preview成功を「Shipmentへ取り込み済み」「発送済み」「配達済み」と読み替えない。

公式code pairの説明表示と、実引受・配達完了をShipmentへ確定保存する処理は別である。非空の14バイト日付値を含む実CSVが不足しており、日時形式と意味は未確定である。

## 26.6 追跡中の確認

追跡状況が必要な間は、送り状・ゆうプリR・日本郵便側で確認できる実際の追跡情報を使用する。アプリの`/shipments`は未発送予定一覧であり、配送会社のリアルタイム追跡画面ではない。

外部で「引受」「輸送中」等が確認できても、現行アプリがその事実を自動保存したとは考えない。画面上のShipment状態、`actualShippedAt`、`trackingNumber`等はそれぞれ独立して確認し、外部の事実とアプリの保存状態を混同しない。

## 26.7 配達完了を確認したとき

日本郵便側で配達完了を確認しても、現行の発送履歴previewだけでは次は自動実行されない。

- `deliveredAt`の保存
- Shipment statusの配達完了更新
- Repair statusの納品済み更新
- 顧客への配達完了LINE送信

未実装の自動処理が完了した前提で案件を閉じない。アプリ側の正式な更新手順が実装・検証されるまでは、外部で確認した配送事実とアプリ内の保存状態を別々に扱う。

## 26.8 結果が分からない場合

「発送したはず」「届いたはず」で状態を進めない。次の順に事実を分ける。

1. 対象Shipmentと送り状・管理番号が一致しているか。
2. 現物を実際に引き渡した記録があるか。
3. 日本郵便側の追跡結果は何か。
4. 発送履歴CSVに対象行があるか。code・日付・追跡番号は何か。
5. アプリ側で保存されているShipment / Repairの状態は何か。

不明な配送codeや矛盾がある場合は、推測で`発送済み`や`配達完了`にしない。正本の考え方は[第35章](35_status-source-of-truth.md)、二重処理防止は[第36章](36_duplicate-safety.md)、障害の切り分けは[第37章](37_troubleshooting.md)を参照する。

## 26.9 この章を更新する条件

Task202Bの公式説明表示は本章へ反映済み。次の保存・通知機能が実装され、productionで実データによる動作確認まで完了した場合に本章を更新する。

- 実CSVに基づく14バイト日付値の形式・意味と実引受判定契約
- 追跡番号の安全なShipment保存
- `actualShippedAt` / `deliveredAt`等の確定ルール
- Shipment / Repair statusの状態遷移
- 追跡番号付きLINE発送通知
- 配達完了からRepair納品済みへの連携
- 重複取込・再実行・競合時の安全策

実装commitだけ、preview成功だけ、外部CSVの推測だけでは「完成」に変更しない。更新時は[第39章](39_manual-update.md)の手順に従い、実装・production・外部結果を照合する。
