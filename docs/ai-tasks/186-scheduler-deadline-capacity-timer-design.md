# Task186: 納期逆算・業務タイマー・分割スケジュール設計

## 目的

Task185の作業時間推定設計を前提に、納期逆算、仕入先リードタイム、見積り・問い合わせ等の非修理業務、複数日作業、業務タイマー、急な中断を自動スケジューラへ接続する業務ルールを記録する。

このTaskは docs-only（設計記録のみ）。schema / migration / API / UI / DB変更は行わない。

## 日数の基本単位

- ランニングテスト: 暦日
- 標準納期3週間: 21暦日
- 仕入先リードタイム: 暦日
- 見積回答後の承認待ち: 通常0〜1暦日を初期目安とする
- WorkCalendarの作業可能時間とは別に、工程日数は日付制約として扱う

## 納期逆算

中核日付:
- `earliestWorkStartDate（最短作業開始可能日）`
- `latestSafeWorkStartDate（安全上の最遅作業開始日）`
- `slackDays（余裕日数）`

`slackDays = latestSafeWorkStartDate - earliestWorkStartDate` とし、余裕が小さい案件を優先する。0未満は納期危険。
## OHの標準工程バッファ

初期案:
- ランニングテスト: 3暦日
- 不具合・再調整バッファ: 3暦日
- 発送遅延バッファ: 1暦日

作業開始日を含め、納品予定日の8日前までに作業開始する考え方とする。

これらはコードへ固定せず、作業条件ごとの標準工程日数として設定可能にする。

候補:
- `standardLeadDays（標準納期日数）`
- `runningTestDays（ランニングテスト日数）`
- `reworkBufferDays（再調整バッファ日数）`
- `shippingBufferDays（発送遅延バッファ日数）`

## 仕入先リードタイム

発注までの待ちと、発注後の配送日数を分離する。

- `plannedOrderDate（発注予定日）`
- `orderedAt（実発注日時）`
- `expectedArrivalDate（入荷予定日）`
- `receivedAt（実入荷日時）`
仕入先・配送方法ごとに以下を表示・保持する方向:
- `manualStandardLeadDays（手動標準日数）`
- `medianLeadDays（実績中央値）`
- `averageLeadDays（実績平均）`
- `p80LeadDays（80パーセンタイル）`
- `maxLeadDays（最大値）`
- `sampleCount（実績件数）`
- `effectiveLeadDays（採用リードタイム）`

初期は手動標準値を採用。実績が20〜30件程度以上たまったらP80を安全側の候補として利用し、中央値・平均・最大値も参考表示する。

複数案件の部品をまとめて発注する場合は、発注予定日までの待ち日数も `earliestWorkStartDate` に含める。

## 取引先別優先設定

生の係数入力より、業務上理解しやすい段階選択を基本とする。

候補:
- 最優先
- 優先
- 標準
- 納期柔軟
- 余裕重視

内部では `priorityFactor（優先係数）` と `scheduleBufferDays（追加余裕日数）` へ変換する方向。
## 見積り時間

初期標準:
- `standardEstimateMinutes（標準見積り時間） = 20分`

案件ごとに `actualEstimateMinutes（実見積り時間）` を1分単位で保存する。

表示する統計:
- 実績件数
- 累計平均
- 累計中央値
- 直近3ヶ月平均
- 直近6ヶ月平均
- 現在採用値

スケジューラでは総負荷を正確に見たいので平均値を一義とする。

採用ルール案:
1. 直近3ヶ月に100件以上あれば3ヶ月平均
2. それ以外で直近6ヶ月に100件以上あれば6ヶ月平均
3. それ未満は20分
4. 累計平均・中央値は常時参考表示

診断開始から金額確定までを見積り時間とする。

## 毎日の予定調整

業務開始後、まず「今日の予定確認・調整」30分を初期予約枠として組み込む。
見積中のRepair（案件）を一覧表示し、その日に見積る対象を選択する。

選択本数 × 現在採用中の標準見積り時間をその日のWorkCalendar容量へ追加し、スケジュールを再計算する。

例: 5本 × 20分 = 100分。

問い合わせ対応は初期60分/日を予約枠として組み込み、実タイマーで実績を蓄積する。十分な実績がたまった後は直近3〜6ヶ月の1営業日あたり平均問い合わせ時間を採用候補とする。

## 受付業務

受付も独立した業務時間として計測する。

主な内容:
- 荷物開封
- 時計と依頼内容確認
- 写真
- 到着登録
- 案件との照合
- 基本情報確認

予定外の受付はクイック開始できるようにする。

受付直後にそのまま見積りする場合も、統計上は受付と見積りを分離する。「見積りへ移行」で受付タイマー停止→同じ案件の見積りタイマー開始を1操作で行う方向。

## 共通業務タイマー

同時に計測中の業務は常に1つだけとする。
別案件・別業務をクリックすると、現在のセッションを自動停止し、新しいセッションを開始する。

過去に停止した作業をクリックすれば再開し、「停止」で何も計測していない状態へ移行可能とする。

業務区分候補:
- 修理
- 見積り
- 受付
- 問い合わせ対応
- 顧客連絡
- 部品・発注
- 発送
- 事務
- その他

予定外受付・予定外見積り・問い合わせ等をクイック開始できるようにする。

タイマー保存は startedAt / endedAt を秒精度で保持し、実績集計・スケジューラ利用時は分単位へ集計する。

## WorkTimeSession

合計時間だけでなく、開始・終了区間を履歴として保持する方向。

候補:
- `activityType（業務区分）`
- Repair / Inquiry / OrderRequest / Shipment 等の関連先
- 主作業
- `startedAt（開始日時）`
- `endedAt（終了日時）`
- 手動修正の有無・理由
- 無効化状態（誤計測対応）

OH中のゼンマイ交換のように主作業に内包される作業で毎回タイマーを切り替えさせず、基本は「現在の主作業」を計測する。

洗浄待ち、接着乾燥、ランニングテスト等の待ち時間は実作業時間へ含めず、工程日数として別管理する。

## 複数日にまたがる修理

修理は1日に全量が収まることを前提にしない。

今日の作業カードには、タイマー操作とは別に以下を設ける方向:
- 作業完了
- 今日ここまで / 翌日以降へ回す

「今日ここまで」では、
`remainingWorkMinutes（残作業時間） = 採用予定作業時間 - 累計実作業時間`
を算出し、残時間を翌日以降の空き枠へ再配置する。

翌日固定ではなく、納期・空き容量・優先度を再計算して翌日以降の適切な日へ置く。

実作業実績が増えて推定値を超過した場合は、残作業時間を0に丸めるだけでなく、必要に応じて人間が残時間を補正できるようにする方向。

## 急な作業中断
修理中に追加不具合が見つかっても、deliveryDateExpected（納品予定日）は即時自動変更しない。

「作業中断」でタイマー停止・残作業時間保存・通常スケジュールから一時除外する。

中断理由候補:
- 追加部品の可能性
- 修復方法検討
- 顧客確認待ち
- 外注待ち
- その他

その後の分岐:
- 修理継続: 残作業時間を再計算して再配置
- 部品手配: OrderRequestと接続し、expectedArrivalDate以降へ再開可能日を移動
- 顧客確認待ち: 回答まで除外
- 判断保留: reviewDate（再確認日）等で放置防止

部品待ち等で `earliestWorkStartDate > latestSafeWorkStartDate` となった場合は納期危険として表示する。

現在納品予定日と、部品到着・残作業・ランニングテスト・再調整・発送バッファから算出した最短納品可能見込日を並べる。

**納品予定日の変更は自動実行せず、人間が承認する。**

## 実効作業容量

WorkCalendarの480分をすべて修理に使える前提にはしない。
業務タイマーから以下を日次・月次で可視化する:
- 総業務時間
- 修理
- 見積り
- 受付
- 問い合わせ対応
- 顧客連絡
- 部品・発注
- 発送
- 事務
- その他
- 未計測時間
- 修理時間比率

十分な実績がたまった後、`effectiveRepairCapacityMinutes（実質修理可能時間）` を提案する。

WorkCalendarを自動で書き換えず、人間が確認して採用する。

## 休日日数シミュレーション

候補日を0分稼働として仮置きし、全案件を再計算する。

表示例:
- 今月あと最大4日程度休業可能
- 特定日を休みにすると納期危険2件
- 1日480分→420分へ変更した場合の影響

月初に休み・半日・私用等をWorkCalendarへ入力し、将来は外部カレンダー取込も検討する。
## 今日の作業・手動再配置UI

案件カードを日別に並べ、予定時間・実績時間・残作業時間を表示する方向とする。

操作候補:
- 開始 / 再開
- 停止
- 今日ここまで
- 作業完了
- 作業中断
- ドラッグによる前日/翌日等への移動

手動移動は、
- ソフト移動: 希望位置を変え、その後の未固定案件を再計算
- 固定: `scheduleLocked（予定固定）` を使い自動再計算でも動かさない
に分ける。

## 全体計算フロー

受付 / 見積
→ 承認
→ 作業時間・標準納期取得
→ 部品入荷可能日算出
→ earliestWorkStartDate
→ 納品予定日から工程バッファ逆算
→ latestSafeWorkStartDate / slackDays
→ 取引先優先設定等で順位補正
→ 見積り・問い合わせ・予定調整等を差し引いた実効容量へ分割配置
→ 実績タイマーで残時間更新
→ 中断・部品待ち時は再開可能日を再計算
→ 人間確認後に納品予定変更
→ 実績蓄積で将来推定を改善
