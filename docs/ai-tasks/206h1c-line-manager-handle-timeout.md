# Task206H1C — LINE Manager non-waiting continuation pin

## Live evidence and review

In the H1B non-sending live smoke, the dedicated profile reached the trusted account login stage and found the exact approved `LINEアカウント` control. `Locator.element_handle(timeout=1)` failed after about 3.7 ms; the same locator with `timeout=10` succeeded, with about 13.8 ms total elapsed. No sender or LINE send was started.

The first H1C draft raised that timeout to 50 ms. Independent review found a High blocker: while `Locator.element_handle` waits, exact button A can disappear and replacement B can appear, allowing B to be clicked. A same-label link can also appear during the wait, bypassing cross-role ambiguity. A second abandoned draft added `evaluate_handle(timeout=50)` and a button/link union `Locator.evaluate(timeout=50)`; these are also waiting Locator operations and leave the same risk. Neither draft is retained.

Final independent read-only review found another High blocker in the next draft: separate button and link `element_handles()` calls did not make cross-role uniqueness a single observation. A button and same-label link could exist during each button query, while the link disappeared only during each link query. All three resolutions could report one button, the identity check could pass, and the button could be clicked despite never being unique. The review also found a Medium documentation/test error: Playwright `dispatch_event` fires without a visibility or enabled actionability guard. The old fake rejected such dispatches, giving false reassurance about the final race.

## Final design

`_continuation` combines exact button and link locators with `or_()` and calls `element_handles()` once on that union. Installed Playwright 1.63 routes this to one `querySelectorAll` request. It returns the current matching DOM handles, or an empty list, without selector wait or timeout. IPC may take longer than 10 ms, but there is no artificial 1 ms acquisition deadline and no wait for a future replacement. More than one exact control, whether in the same role or across roles, fails as ambiguous at that single snapshot instant.

For the sole handle, an `ElementHandle.evaluate` descriptor reads native/explicit button or link semantics, href, and connection status from that concrete node. Unknown semantics fail closed. The node must also be visible and enabled. Links require a nonempty trusted href; any href on a button must also be trusted. The descriptor and trust checks run again on the current node before dispatch. No sequential role locator query is used for classification.

The existing five-second, 250 ms render poll checks trusted stage and credential/challenge UI on every pass. After readiness, the caller makes a fresh union snapshot and pins its concrete handle. A replacement before this fresh pin may become the selected current control, as in H1B. Before dispatch, a second non-waiting union snapshot checks current uniqueness, role, visibility, enabled state, and href. Direct DOM identity comparison proves the sole current exact node is the pinned node. Stage and challenge checks surround this recheck. If the node changed, disappeared, became invalid, or gained an ambiguous peer before the recheck, the path fails without retry or click.

Only exact `LINEアカウント` then exact `ログイン` on the existing trusted stages can be clicked, at most twice. Activation uses `ElementHandle.dispatch_event("click")` on the pinned node; it never uses `Locator.click` or a Locator actionability wait. Final chat validation remains unchanged. A finite micro-race remains after the last identity/stage/challenge checks: visibility, enabled state, role, href, or ambiguity could change before dispatch. `dispatch_event` itself is not an actionability guard and may fire on an invisible or disabled node. Detached behavior at dispatch was not live-verified.

## Same-Task follow-up from non-sending live evidence

The dedicated Chrome profile reached `https://account.line.biz/login` after the `chat.line.biz` redirect. The exact existing `LINEアカウント` control appeared once and click 1 succeeded. The next stage was `https://access.line.me/oauth2/v2.1/login`, not `/authorize`; it had no credential or challenge UI and had exactly one existing `ログイン` control. Click 2 succeeded and immediately reached `https://access.line.me/oauth2/v2.1/ssoLogin` without credential or challenge UI. That path was transition-only: no third click or credential entry occurred. The profile then became authenticated, and a later `chat.line.biz/` visit opened directly. The current `--ensure-valid` succeeded with `verified=true`, `recovered=true`, `cookie_count=11`, and `bot_count=1`. No LINE sender or LINE send occurred.

The exact `/oauth2/v2.1/login` path is now an eligible interactive access stage for the second approved control; the exact `/authorize` path remains compatible. `/oauth2/v2.1/ssoLogin` is separate from `_trusted_stage`, cannot enter `_continuation`, and cannot cause another click. After click 2, a bounded 10-second, 250 ms poll checks the current URL and challenge state on every pass. It allows only the current access URL before navigation, then the exact SSO transition URL, then the exact chat root; direct transition to chat root also succeeds. Any other URL or visible credential/challenge UI fails closed. The existing exact labels, two-click limit, single non-waiting union snapshot per control resolution, descriptor/href trust, DOM identity checks, and final chat-root requirement remain in place.
