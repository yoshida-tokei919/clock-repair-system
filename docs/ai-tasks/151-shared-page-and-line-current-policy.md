# Task151補足: 顧客共有ページ・LINE運用 現行方針

更新日: 2026-09-06

## 目的

顧客対応を、LINEでの会話と共有ページでの確定情報確認に分ける。

基本方針:

```txt
LINE = 会話
共有ページ = 確定情報・意思決定
修理アプリ = 永続的な案件記録
```

共有ページをチャット代替にしない。

---

## 1. LINEと共有ページの役割分担

### LINE

主に以下を扱う。

- 問い合わせ
- 概算見積
- 修理方針の相談
- お客様の希望確認
- 長文説明
- 細かいラリー

### 共有ページ

主に以下を扱う。

- 本見積
- 承認
- 進捗
- 状態写真
- 見積書
- 納品書
- 請求書
- 保証書

本見積を出す時点では、金額・作業方針は原則確定済みとする。

事前相談との差異もLINE等で説明したうえで本見積へ進むため、共有ページの見積スペースは過度に大きくしない。

一方で、案件固有の補足を柔軟に書ける説明文スペースは十分確保する。

共有ページのコメント機能は通常チャットの代替にしない。見積に直接関係する修正依頼・補足用途へ限定する方向。

## 2. LINE履歴保存に関する現時点の判断

### 受信

既存Webhookで `LineUser` を取得できる。

既存の `LineUser -> Customer` 紐付けを利用し、将来的に受信本文を永続化することは可能。

### 送信

LINE Official Account Managerから手動送信した本文を、通常のMessaging API / Webhookで完全取得する公開仕様はない。

### PC Manager自動操作案

Chrome Extension / Node agent / Power Automate Desktop / AutoHotkey等でOfficial Account Manager Webを自動操作し、スマホの修理アプリからPC経由で通常チャット送信する案を調査した。

結論:

**No-Go**

理由:

- 公開された安定トークIDがない
- 安定したトーク遷移APIがない
- Manager送信完了を保証する公開API/コールバックがない
- DOM/UI変更依存が大きい
- 誤った顧客トークへ送信した場合、機械側で安全に検出できない
- 規約解釈がグレー

表示名検索、座標クリック、一覧順依存は採用しない。

### n8n

n8n自体にはこだわらない。

Manager操作の正規APIがないため、n8nを挟んでも根本問題は解消しない。

### 擬似LINE画面

Customer単位の擬似LINE timelineをアプリ側に作る構想は成立する。

将来採用する場合の自然な構造:

```txt
Customer
  -> LineConversation
      -> LineMessage
          -> repairId nullable
```

ただし、スマホからの送信で「下書き保存 -> コピー -> LINEへ貼付」を必須にする案は採用せず、現時点ではLINE完全履歴統合自体を保留する。

## 3. B2B共有ページ Task151 現在の修正

以下はローカルで実装済みだが、2026-09-06時点でまだcommit前。

対象:

- `src/app/customer/repairs/[token]/page.tsx`
- `src/app/customer/repairs/[token]/CustomerExportTools.tsx`

修正:

- 金額メモ内 `ご案内金額` -> `金額`
- 貴社用データ出力設定 `管理番号` -> `貴社管理番号`
- 貴社用データ出力設定 `ご案内金額` -> `金額`
- `B2B専用` ラベル非表示
- 承認 / 差戻しボタンを「お客様への説明文」の上へ移動
- お客様への説明文の未設定時デフォルト文章を廃止し空欄化
- 既存保存済み説明文は維持
- ステータスを大きいpill表示へ変更
- 税抜小計 / 消費税 / 税込合計を表示

### 税込合計修正

旧共有画面は税抜明細小計をそのまま「税込合計」として表示していた。

既存の正式ロジックに合わせる。

```txt
消費税 = Math.floor(税抜小計 * 0.1)
税込合計 = 税抜小計 + 消費税
```

帳票/PDF側の既存計算は変更しない。

## 4. B2B共有ページ デザイン改善方針

現在の機能的な白主体UIが殺風景なため、以下の方向で改善する。

- ページ全体背景: ごく薄いブルーグレー
- 最上部カード: 必要なら時計/ムーブメント写真を5〜8%程度の透過で背景利用
- 写真は装飾であり主役にしない
- 案件ヘッダー: ステータスに応じた非常に薄い色面
- ステータスpill: 現状より明確に大きく
- 見積内容ヘッダー: ごく薄いblue accent
- 税抜小計 / 消費税: 控えめ
- 税込合計: 最終結果として強調
- 承認/差戻し領域: 次の操作と分かるよう区切る
- 説明文空欄時: 大きな空カードを残さない方向
- 金額メモ: 補助機能として控えめ
- 貴社用データ出力設定: ページ下部の業務用utilityとして本体より控えめ

未実装部分は、Task151の実装済み変更と混同しないこと。

## 5. B2C共有ページ 基本思想

B2CはB2Bの色違いにはしない。

一般顧客が小さいスマホ画面でも迷わず理解・判断できる構造にする。

### 業務フロー上の前提

問い合わせ・概算・選択肢・希望確認・修理方針のラリーは、本見積前にLINEで行う。

時計受領後、実物確認による事前打合せとの差異も説明したうえで、本見積を出す。

したがってB2C共有ページでは、長い意思決定会話を再現しない。

### 初期表示で見せる情報

時計ごとのcardを基本とし、折りたたみ時でも以下が分かるようにする。

- 時計写真
- 大きいステータスpill
- ブランド / モデル / Ref / Cal等の主要識別情報
- 見積合計（税込）
- 主な作業 2件程度 + `ほか`

詳細はaccordionで展開する。

### 複数本案件

佐藤様案件のような3本同時依頼を前提にする。

ページ上部に全体summaryを置き、各時計は独立cardにする。

例:

```txt
3本お預かり
見積確認 2件
作業中 1件
完了 0件
```

### 進捗

視覚的な進捗表示を検討する。

```txt
受付 -> 状態確認 -> 見積 -> 承認 -> 作業 -> 完了
```

内部statusをすべてそのまま出すのではなく、顧客が理解しやすい表現を優先する。

### 状態写真

各時計cardから状態写真を確認できるようにする。

### 関連書類

案件状況に応じて以下への導線を表示する。

- 見積書
- 納品書
- 請求書
- 保証書

未作成書類を有効ボタンとして見せない。

### 説明文

見積明細自体は省スペースでよい。

一方、実物確認後の状態・事前打合せとの差異・今回の修理理由等を柔軟に書ける「修理内容のご説明」欄は比較的大きめに取る。

## 6. B2C承認UI

見積確認中の案件だけ承認操作を表示する。

主ボタン候補:

```txt
この内容で進める
```

`差戻し` はB2Cには業務用語のため、顧客表示は次のような自然な文言にする方向。

```txt
相談・修正をお願いする
```

作業中 / 完了案件では承認ボタンを表示しない。

---

## 7. B2Cデザイン方向

- white + soft blue-gray
- headerにごく薄い時計写真
- 大きめ文字
- 十分な余白
- rounded card
- shadowは弱く
- ステータスは強く
- 見積明細はcompact
- 詳細説明 / 写真 / 書類は必要に応じて展開

高級時計ブランドLPではなく、信頼できる修理portalを目指す。

---

## 8. 佐藤様案件から得た設計上の教訓

- 長い相談や選択肢確認は共有ページよりLINEが適切
- `Tropic38を試し、不可なら代替案` のような分岐は本見積前に希望と優先順位を確認する
- 最終的に工房判断へ委ねてもらうケースも多い
- 本見積は最終確定に近く、共有ページで再び長い意思決定を要求しない
- ただし案件固有の説明欄は重要
- 複数時計案件では全体summary + 時計ごとの独立cardが必要

## 変更禁止の注意

B2C共有ページ実装時も、以下を勝手に変更しない。

- 既存帳票PDF内容
- 見積書 / 納品書 / 請求書 / 保証書生成ロジック
- LINE送信仕様
- LINE Webhook署名検証
- RepairEntryForm
- PublicCase
- PricingRule
- RepairLineItem snapshot

共有ページは既存の確定データを表示するconsumerであり、マスタや価格ルールを後読みして過去表示を変えない。
