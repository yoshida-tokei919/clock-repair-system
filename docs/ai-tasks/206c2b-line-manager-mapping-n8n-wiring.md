## Repository contract

`scripts/start-line-manager-mapping-n8n.ps1` is the fixed n8n Execute Command entry point. Its fixed Windows named mutex serializes the entire mapping run and alert-state update across both triggers, independently of n8n concurrency. It waits at most five minutes. This mutex is separate from the sender-service singleton and shared short-lived `lineoa-operation.lock` introduced by Task206C2C. Once acquired, the adapter invokes the fixed `scripts/start-line-manager-mapping.ps1 -Apply` once in a separate Windows PowerShell process. The child continues to own its User-environment token and fixed production settings. No LINE send is enabled.

The adapter limits the child to 240 seconds and polls its exit and output file lengths every 200 ms. It drains stdout and stderr concurrently to unique temporary files, fails if stdout exceeds 4 KiB or stderr exceeds 64 KiB while the child runs, never reads or emits stderr, and removes both files. The child PowerShell first blocks on a fixed stdin startup gate; only after the adapter creates and configures a Windows Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and assigns the child does it release the gate to invoke C2A `-Apply`. No mapping descendant can start before assignment. On timeout or overflow, the adapter terminates the Job. If the root exits while the Job still has active processes, it treats the result as `configuration_failure` and terminates the Job. Pipe drain is bounded by the remaining 240-second budget. The Job handle closes before the mapping mutex is released, so Windows terminates any remaining Job processes even if explicit termination fails. If Job setup or assignment fails, the gate stays closed and a fixed `taskkill.exe /PID <root> /T /F` stops the still-gated child. It accepts exactly one C2A status/count line and emits exactly one compact JSON line with these seven keys: `status`, `candidateCount`, `scannedChatCount`, `safeMatchCount`, `runnerExitCode`, `healthy`, `alertDue`. The adapter always exits 0. Lock timeout, child timeout, missing runner, process-start or Job failure, malformed/oversized output, and invalid exit/status pairs produce sanitized zero-count `configuration_failure` with `runnerExitCode: -1` and `healthy: false`. There is no mapping retry.

The exact C2A Python `main()` exit contract is:

| Child status | Child exit | Adapter healthy |
| --- | ---: | --- |
| `healthy_no_candidates`, `verified` | 0 | true |
| `pending_no_exact_match`, `pending_ambiguity` | 0 | false |
| `mapping_conflict`, `manager_live_read_unavailable`, `internal_api_unavailable`, `configuration_failure`, `lineoa_operation_busy` | 1 | false |

The adapter rejects any other pairing. A Manager read failure is not proof of expired authentication. Mapping remains based only on immutable exact message IDs.

The adapter stores only `lastUnhealthyStatus` and `lastAlertAt` at `%LOCALAPPDATA%\clock-repair-system\line-manager-mapping-n8n\alert-state.json`. Under the mutex, a new unhealthy status or the same status at least six hours after its last alert sets `alertDue: true` and updates that file **before** the Slack attempt. Repetition within six hours sets `alertDue: false` without changing the timestamp. Either healthy status deletes the state and emits no recovery Slack message. A unique local temp file is atomically replaced where supported; on a constrained filesystem a move over the destination is used while the mutex is held. State read/write failure fails closed to sanitized `configuration_failure` with `alertDue: true`; lock failure does the same without touching state. The state stores no IDs, content, tokens, errors, or paths.

`scripts/reset-line-manager-mapping-alert-n8n.ps1` is the fixed local compensation action for final Slack alert failure. It accepts no arguments, token, or network access. It acquires the same named mutex with a five-minute wait, deletes only the fixed `alert-state.json` if present, and emits one fixed sanitized `status=alert_state_reset` or `status=alert_state_reset_failed` line. A successful Slack alert leaves state in place. A final failed Slack alert invokes the reset action so the next trigger can retry the same status; reset failure is observable only through its sanitized status and must be investigated without exposing the raw Slack error.
