# Task211B — Pre-approval work execution / 先行作業

Production: future / not started

## Background

FMPではステータス遷移が自由で、見積り・承認が未入力のままでも作業完了を記録できた。実務では電池交換など低額・短時間の定型作業を、見積り中に「承認される可能性が高い」と判断して先に完了させることがある。

現行アプリの `見積り待ち -> 承認待ち -> 作業待ち -> 作業中 -> 作業完了` を単一直列の必須経路にすると、この実務を表現できない。

## Core policy

- 見積 / 承認の商流状態と、実作業の進捗を分離して扱える方向にする。
- `見積り中 / 未承認 / 作業完了` の組み合わせを正しく表現できるようにする。
- 先に作業した事実を、承認済みへ偽装して表現しない。
- 「顧客が上限金額まで事前承認済み」と「顧客承認はまだないが工房判断で先行作業」は別概念として記録する。
- 電池交換等の作業種別だけで自動的に承認不要・先行作業可へハードコードしない。案件ごとの判断を正本とする。

## Expected UX

- 見積り中 / 承認前でも、管理者が明示操作で `先行作業として開始` を選べる。
- 先行作業開始時に理由、開始日時、操作者を監査可能な形で残す方向とする。
- 作業完了後も見積 / 承認が未完了なら、画面上で `作業完了 / 見積・承認未完了` を明示する。
- 金額確定後、正式な事前承認範囲内なら通常の後工程へ進める。承認が必要なら作業済みでも承認待ちを保持できる。
- 未承認の先行作業完了を理由に、顧客承認済み・請求確定済み・発送可能と自動判定しない。

## Investigation scope before implementation

- 現行 `Repair.status`、Estimate / approval、RepairWorkPlan、WorkTimeSession、Schedulerの責務を再確認し、最小変更で状態を直交化できるか調査する。
- 共有ページ、作業完了通知、請求、Shipment等が `作業完了 = 承認済み` を暗黙前提にしていないか確認する。
- 既存の「料金確定済み / 上限金額まで事前承認」の設計と重複しない形にする。
- schema / migrationが必要な場合は高リスク変更として実装担当と独立レビュー担当を分離し、Data API / GRANTも確認する。

## Validation targets

- 見積未確定・未承認の案件でも、明示操作により先行作業を開始・完了できる。
- その状態でも承認状態は未承認のまま保持され、履歴上も誤認しない。
- 事前承認案件は従来どおり承認範囲内なら不要な承認待ちを省略できる。
- 先行作業済み案件で、見積確定・承認・請求・発送の各gateが安全に機能する。
- B2B / B2C双方で利用でき、特定作業種別だけの例外実装にしない。
