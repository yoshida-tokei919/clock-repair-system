# B2C問い合わせ〜納品 顧客導線・連絡方針 — 2026-10-12

## 目的

B2Cのお客様がLINE問い合わせをしてから納品されるまでの、状況確認・LINE連絡・フォーム回答・Shipmentの役割を一本化する。

基本の役割分担は以下とする。

- LINE: 会話と重要な節目の通知
- 顧客共有ページ: 継続的な修理状況確認と確定情報
- 専用フォーム: 受付・返送先・配達希望など、お客様の明示回答
- 時計修理業務アプリ: Inquiry / Customer / Repair / Shipment等の業務データ正本

内部ステータスが変わるたびにLINEを送る運用にはしない。お客様が行動・判断する必要がある節目はLINEで知らせ、日常の進捗は共有ページで確認できるようにする。

## 受付フォーム完了後の共有ページ

現行の送付受付・返送先フォームでは、お客様がフォームを送信した時点で対象時計ごとに `Watch + Repair` を自動作成している。各Repairはまず `送付待ち` で開始する。

今後の標準導線は以下とする。

1. お客様が送付受付・返送先フォームを送信する。
2. 現行どおり対象時計ごとのRepairを自動作成する。
3. 同じ受付で作成されたRepairをまとめて確認できる共有ページURLを1つ用意する。
4. そのURLを既存のLINE通常トーク経路で1回案内する。
5. 以後、見積・承認・修理進捗・作業完了・発送・配送状況・納品まで同じ共有ページを状況確認の入口として使う。

複数本受付でもRepairごとにURLを複数送らない。

共有ページは単なる「見積確認ページ」ではなく、受付後から納品まで継続して使う**修理状況ポータル**として扱う。

## 共有ページの役割

共有ページはチャットの代替にはしない。

必要に応じて以下を表示する。

- 時計 / Repairごとの現在状態
- 見積内容・税込合計
- 承認状況と承認操作
- お客様向け説明文
- 状態写真・作業完了写真
- 前受金情報
- 将来のShipment / tracking情報

`作業待ち`、`部品待ち`、`作業中`、`作業完了`などの通常ステータス変化は共有ページへ反映するが、それだけを理由にLINE通知を毎回送らない。

## 同一顧客に複数Repairがある場合

### 原則

同一顧客の複数Repairは**原則まとめ発送**とする。

お客様にRepair件数分の配達希望フォームを回答させない。

### 一部だけ作業完了した場合

例:

- Repair A: 作業完了
- Repair B: 作業完了
- Repair C: 長期部品待ち

共有ページでは3本それぞれの現在状態を表示する。

発送判断が必要になった段階で、お客様へ1回だけ以下を確認する。

- 完成済みRepairを先に発送する
- 未完了Repairも完成するまで待ってまとめて発送する

残りのRepairが数日程度で完成する見込みなら、1本目・2本目の作業完了時点では発送確認を送らず、全件が揃ってから発送確認してよい。

### 分割発送

複数口発送は例外運用とする。

通常のお客様画面で最初から「2口」「3口」を選ばせ、1口目・2口目ごとにRepairを細かく組ませるUIは作らない。

実務上必要になった場合だけ、詳細な分割発送操作を追加・表示する方向とする。

## 配達希望とShipment

配達希望はRepair単位ではなく、**Shipment / 今回発送するRepairグループ単位**で扱う。

標準フロー:

1. 今回発送するRepairを確定する。
2. お客様が配達希望を1回回答する。
3. 回答内容は `希望なし / 日付 / 時間帯 / 日付+時間帯` を扱う。
4. 選択されたRepairで `DRAFT` Shipmentを自動作成する。
5. 配達希望をShipmentへ反映する。

既存の手動Shipment作成は、例外・fallback運用として残す。

### DRAFT中の変更

Shipmentが `DRAFT` の間は以下を許可する。

- 管理画面から配達希望を手動変更
- お客様が配達希望フォームを再回答
- 対応するShipmentが一意ならフォーム変更をShipmentへ自動反映

### 送り状発行依頼後

`ゆうプリクラウド発行を依頼` を押してShipmentが `READY` 以降になったら、通常の配達希望フォームからの変更はlockする。

送り状発行後の配達希望変更は、Shipmentの値だけを書き換えず、既存送り状の扱いを含めた**訂正 / 再発行フロー**で処理する。

## ゆうプリクラウド送り状発行

管理画面の `ゆうプリクラウド発行を依頼` ボタンを人間の明示承認として残す。

想定フロー:

```text
DRAFT Shipment
→ ヨシダが「ゆうプリクラウド発行を依頼」
→ READY
→ local Workerが検出
→ JP Business ToolBox / ゆうプリクラウドへログイン
→ CSV登録
→ 送り状発行
→ trackingNumber取得
→ PDF取得
→ NEC MultiWriter 5750Cへ印刷
→ LABEL_ISSUED
```

送り状を印刷しただけでは発送済みにしない。

## 実発送・配送追跡・納品

実発送イベントは日本郵便の**「引受」**とする。

目標フロー:

```text
LABEL_ISSUED
→ 日本郵便の引受を検知
→ Shipmentを発送済みに更新
→ actualShippedAt保存
→ Repairを発送済みに更新
→ 追跡番号付きLINE発送通知
→ 日本郵便Web追跡を自動同期
→ 輸送中 / 配達中 / 配達完了
→ Repairを納品済みに更新
```

配送中の通常状態変化ではLINEを連続送信せず、共有ページで確認できる方向とする。

配達完了後の追加LINEは必須にせず、必要な場合だけ送る。

## LINEを送る主な節目

LINEは以下を中心にする。

1. 問い合わせ返信・確認
2. 送付受付・返送先フォーム案内
3. 受付フォーム完了後の共有ページ初回案内
4. 見積完成・承認依頼
5. 重要な例外・判断依頼
6. 発送判断・配達希望確認
7. 日本郵便引受後の発送通知 + 追跡番号
8. 配達完了後は必要な場合のみ追加連絡

各Repairの内部ステータス変更だけを理由にLINEを送信しない。

## 今後の実装優先順

1. 受付フォーム完了 → 同じ受付のRepairをまとめた共有ページURL → LINE通常トーク送信
2. 複数Repairを1共有ページで安定して表示
3. 顧客単位の複数Repair発送判断
4. Shipment / 発送グループ単位の配達希望回答
5. 配達希望確定後のDRAFT Shipment自動作成
6. `ゆうプリクラウド発行を依頼` を明示承認として維持し、その後をWorkerで自動処理
7. 日本郵便Web追跡同期
8. 引受 → Shipment / Repair発送済み → 追跡番号付きLINE
9. 配達完了 → Repair納品済み

## 旧方針との優先関係

旧Task203の「Repairごとに作業完了LINEを送り、そのRepairの配達希望を取得する」という前提と競合する場合、**同一顧客に複数Repairがあるケースでは今回の顧客単位発送方針を優先**する。

単一Repairの場合は、現在の作業完了・配達希望フローを `1 Repair → 1発送グループ → 1 Shipment` としてそのまま利用できる。
