# Task185: 作業時間推定・実績学習 設計

## 目的

Task184のシンプル自動スケジューラーが使用する `estimatedWorkMinutes（推定作業時間）` を、案件ごとの手入力中心ではなく、作業条件・時計情報・過去の実作業時間から自動算出できるようにするための設計方針を記録する。

このTaskは docs-only（設計記録のみ）。schema / migration / API / UI / DB変更は行わない。

## 最優先ルール

- **同一条件の実作業時間実績が存在する場合は、その実績を一義情報として採用する。**
- 同一条件の修理実績は、初期ルールとして実績0件では一般条件標準、1〜9件では実績中央値、10件以上では実績平均値を現在採用値とする。件数閾値・集計方法はスケジューラ設定から変更可能にする。
- 標準作業時間は、実績が存在しない組み合わせを推定するためのfallback（代替値）として使う。
- 標準作業時間と実作業時間は両方保存し、標準値を実績値で消さない。
- 実績は案件ごとの履歴を保持し、最後の1件だけで過去実績を上書きしない。
- 推定結果は合計値だけでなく、可能な範囲で採用根拠を確認できるようにする。

## 内装と外装の共通原則

- 内装と外装は別々に時間計算し、最後に単純加算する。
- 内装作業と外装作業を同時に行うことで相互の時間を短縮する補正は行わない。
- 複合作業による時間短縮は、内装同士または外装同士の範囲だけで扱う。
- 各時間は整数分で保存し、入力UIは10分刻みを基本とする。
## 内装の標準作業時間

標準時間設定画面では、Cal固有値ではなく一般条件の組み合わせで標準値を作る。

主な条件:
- `movementType（ムーブメント種別）`: 機械式 / クォーツ
- `additionalFunctions（追加機能）`: デイト、デイデイト、クロノグラフ、トリプルカレンダー、レトログラード、ツインバレル、トゥールビヨン、ミニッツリピーター、クォーターリピーター、永久カレンダー等
- `workName（作業名）`
- `additionalWork（追加作業）`
- `standardMinutes（標準作業時間）`

「自社ムーブ」は追加機能とは別概念とし、必要なら `movementOrigin（ムーブメント由来）` 等の別属性として実装時に検討する。

## 内装の実作業時間

案件側では MovementCaliber（Cal）を既存時計情報から取得し、修理明細の作業条件と組み合わせて実績を保存する。

優先順位の基本案:
1. Cal + 条件が一致する現在採用値（初期: 実績1〜9件=中央値、10件以上=平均値）
2. Base Cal（ベースCal）+ 条件が一致する現在採用値（実装前調査で必要性を確認）
3. movementType + additionalFunctions + workName + additionalWork の標準時間
4. より一般化した標準時間
5. 該当なしなら時間未設定として人間確認

例: 機械式 + デイト + OH の一般標準が180分でも、ROLEX Cal.3135 + 同条件の実績が蓄積した場合は、設定された件数閾値・集計方法に従うCal別の現在採用値を優先する。
## 複合作業

単体作業と複合作業の両方を登録できるようにする。

複合作業では「組み合わせ全体の総時間」を無制限に列挙するのではなく、基本作業に対する追加作業の同時施工時追加時間を持てるようにする。

例:
- Cal.3135 OH = 150分
- ゼンマイ交換単体 = 30分
- OH中のゼンマイ交換 = +0分
- 切替車交換単体 = 20分
- OH中の切替車交換 = +5分
- よって OH + ゼンマイ交換 + 切替車交換 = 155分

ただし、同一の作業条件・組み合わせについて実作業時間の前例が存在する場合は、標準値から再計算した推定より、設定された実績採用ルールによる現在採用値を優先する。

実装時には、単体レコード、複合作業補正レコード、案件実績レコードをどの物理テーブルへ分けるかをschema調査後に確定する。

## 外装の標準作業時間

外装はブランドよりも「修理箇所 × 作業名」が作業時間への影響が強い。

標準時間の主条件:
- `repairLocation（修理箇所）` または既存の対象部品名構造
- `workName（作業名）`
- `additionalWork（追加作業）`
- `standardMinutes（標準作業時間）`

標準値設定では Brand / Model / Ref に依存しない一般値を登録し、個別実績と共存させる。
## 外装の実作業時間

案件側では Brand（ブランド）/ Model（モデル）/ Ref を既存時計情報から取得し、修理箇所・作業名・追加作業と組み合わせて実績を保存する。

実績検索の優先順位:
1. Ref + 作業条件が一致する現在採用値
2. Model + 作業条件が一致する現在採用値
3. Brand + 作業条件が一致する現在採用値
4. 一般標準時間 × exteriorWorkRiskFactor（外装作業リスク係数）
5. 該当なしなら時間未設定として人間確認

外装ではRefが最も確実な一致条件、次にModelとする。

## ブランド別外装リスク係数

高額時計・外装部品の価値、傷や破損を避けるための慎重さを、実績がない場合の標準時間補正として扱う。

- BrandMaster（ブランドマスタ）に `exteriorWorkRiskFactor（外装作業リスク係数）` を持たせる方向。
- 初期はブランド単位の1係数とする。
- 例: 標準1.00、慎重な作業が必要なブランド1.10〜1.20程度。
- **実作業時間の実績が存在する場合はリスク係数を追加適用しない。**
- 作業別リスク係数は精度向上余地として残すが、初期は設定・保守負荷を優先して導入しない。
- 実運用で特定作業だけ推定差が大きいことが継続的に確認された場合、BrandWorkRiskSetting（ブランド別作業リスク設定）等を再検討する。

## 作業時間設定画面

スケジューラとは別に専用の「作業時間設定」画面を設ける。

UI方針:
- 表形式
- 内装 / 外装を分ける
- 条件項目は既存マスタから dropdown（ドロップダウン）選択
- additionalFunctions（追加機能）は複数選択を想定
- standardMinutes（標準作業時間）と actualMinutes（実作業時間）の両方を入力・保存可能
- 時間入力は10分刻み
- キーボード上下キーで±10分
- desktopでは入力欄フォーカス中のマウスホイールで±10分を候補とする
- mobile向けに -10 / +10 操作も検討する

内装の標準設定ではCalを必須にせず、movementType / additionalFunctions / workName / additionalWork を選択して標準時間を登録する。

外装の標準設定ではBrand / Model / Refを必須にせず、repairLocation / workName / additionalWork を選択して標準時間を登録する。

## Repair（案件）画面の「作業時間」タブ

案件詳細に「作業時間」タブを追加する方向とする。

案件情報から自動表示:
- 内装: Brand / Cal / movementType / additionalFunctions
- 外装: Brand / Model / Ref / repairLocation
- RepairLineItem（修理明細）から workName / additionalWork

表には最低限以下を表示する。
- 作業内容
- 標準推定時間
- 現在の採用時間
- 採用根拠（Cal/Ref等の実績採用値、標準値、複合作業補正、ブランドリスク等）
- actualWorkMinutes（実作業時間）入力欄

案件でactualWorkMinutesを入力した場合、その案件の条件付き実績として履歴保存する。
同一条件の実績は個別履歴を保持し、初期ルールとして実績0件では一般条件標準、1〜9件では実績中央値、10件以上では実績平均値を現在採用値とする。平均値・中央値・件数は常時表示し、閾値と集計方法はスケジューラ設定から変更可能にする。

## estimatedWorkMinutes（推定作業時間）の算出フロー

1. Repair（案件）から Cal / Ref / Model / Brand 等を取得
2. RepairLineItem（修理明細）から作業条件を取得
3. 条件一致する実作業時間実績を検索
4. 実績がある場合はスケジューラ設定の採用ルールに従い、初期値として1〜9件は中央値、10件以上は平均値を採用
5. 実績がない場合は標準作業時間を検索
6. 内装内の複合作業補正を適用
7. 外装内の複合作業補正を適用
8. 外装で実績がない場合のみブランドリスク係数を適用
9. 内装合計 + 外装合計
10. `estimatedWorkMinutes（推定作業時間）` に反映
11. Task184の自動スケジューラがその値を使用

推定結果の例:
- Cal.3135 OH: 現在採用値【実績件数に応じて一般標準 / 中央値 / 平均値】
- ゼンマイ交換: 0分【OH同時作業】
- 風防交換: 40分【標準時間 × ブランドリスク】
- ケース仕上げ: 60分【Ref実績の現在採用値】
- 合計: 250分

## 実装前の必須調査

次の実装Taskでは、schemaを推測せず以下の既存定義を確認してからモデルを決める。

- MovementCaliber（ムーブメントCal）/ Base Cal（ベースCal）
- movementType（ムーブメント種別）の現行保持場所
- Calの追加機能属性の現状
- RepairLineItem（修理明細）
- 内装作業マスタ
- 外装作業マスタ
- BrandMaster（ブランドマスタ）
- Model / Ref の既存関連
- `estimatedWorkMinutes` の更新タイミング
- 案件実績時間履歴の保存方法
- 複合作業ルールの保存方法
- Data API利用有無と必要なGRANT（新規テーブルを作る場合）

schema / migration / RLS / GRANT は高リスク変更として、実装担当と独立レビュー担当を分離する。

## 今回の確定事項

- 実作業時間を一義情報とする。
- 修理実績は、実績0件では一般条件標準、1〜9件では実績中央値、10件以上では実績平均値を初期ルールとして現在採用値にする。件数閾値・集計方法はスケジューラ設定から変更可能にする。
- 標準時間と実作業時間は両方保存する。
- 内装と外装は別計算し、最後に加算する。
- 内装と外装間では複合作業による時間短縮を行わない。
- 内装ではCal固有の実績を強い一致条件として扱う。
- 外装ではRefを最優先、次にModelとする。
- 外装標準時間は修理箇所 × 作業名を中心とする。
- ブランド別外装リスク係数をBrandMasterに持たせる方向とする。
- リスク係数は実績値には適用しない。
- 作業別ブランドリスク係数は初期導入せず、実運用で差が大きい場合に再検討する。
- 作業時間設定専用画面を設ける。
- Repair（案件）画面に「作業時間」タブを追加する方向とする。
- 案件から実績を蓄積し、将来案件の推定精度を上げる。
