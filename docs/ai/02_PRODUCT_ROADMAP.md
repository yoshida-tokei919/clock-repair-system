# PRODUCT ROADMAP

このファイルは、時計修理業務アプリ全体の現在地、全体方針、開発フェーズ、今後の開発順序を管理する正本文書である。

過去の変更履歴は残さない。現在有効な方針だけを書く。
個別Taskの詳細や一時的な調査内容は書かない。

## 全体目的

時計修理業務における以下を一つの業務アプリで管理する。

- 受付
- 見積
- 修理明細
- 内装作業
- 外装作業
- 内装部品
- 外装部品
- 部品検索
- 部品発注
- 在庫
- 案件識別と現場運用
- 帳票
- 顧客共有
- 作業可能判定
- 作業優先順位
- 作業スケジュール
- 事例公開

## Phase 1: 作業マスタ

### 状態

一旦完了。

### 目的

内装作業・外装作業を構造化して入力できるようにする。

### 対象

- RepairWorkCategory（作業カテゴリ）
- RepairWorkAction（処置マスタ）
- RepairWorkName（作業名マスタ）
- PricingRule（価格ルール）
- RepairLineItem（修理明細）

### 方針

- 内装と外装は分ける
- 内装/外装の処置を混在表示しない
- 部品マスタと作業マスタを混同しない
- PricingRule（価格ルール）は価格ルールとして残す
- 作業マスタは帳票・共有ページ・PublicCase（公開事例）へ直接表示しない
- 表示値はRepairLineItem（修理明細）側にsnapshot（保存時点表示値）を保持する

### 現在の完成状態

- 内装LABOR（内装技術料）を構造化入力できる
- 外装LABOR（外装技術料）を構造化入力できる
- external_labor（外装技術料）とpart_external（外装部品行）は分離されている
- business（B2B）/ individual（B2C）別にPricingRule（価格ルール）を保存・取得できる
- 内装/外装の処置候補は分離されている
- 外装PricingRule（外装価格ルール）は保存後の同条件入力で候補再表示される
- modelId（モデルID）あり候補はmodelId=null（モデル共通候補）より優先される
- 編集画面で保存済み外装LABOR（外装技術料）の表示は維持される
- part_external（外装部品行）はPricingRule（価格ルール）保存対象外

## Phase 2: 部品マスタ・部品検索・発注連携

### 状態

進行中。現在は内装部品マスタをCal別実部品中心へ再設計し、メーカー資料・多言語名称・カテゴリー・解説書連携を整理している。

### 目的

内装部品・外装部品を検索、在庫、価格、発注に使える形へ整理する。

内装部品はメーカー横断の完全な日本語標準名を先に完成させる方式ではなく、movementCaliber（ムーブメントCal）ごとの実部品を、メーカー資料を根拠に段階的に蓄積できるようにする。

### 対象

- PartCategoryMaster（標準部品カテゴリ）
- PartNameMaster（標準部品名マスタ）
- PartsMaster（実部品・在庫マスタ）
- PartGradeMaster（部品グレード）
- 多言語部品名称 / PartNameTerm相当
- TechnicalDocument（解説書）
- CalとTechnicalDocumentの関連
- Supplier（仕入先）
- OrderRequest（発注依頼）
- 部品検索ワード生成
- 複数サイト検索
- 通貨変換
- 価格クリック挿入

### 方針

- PartsMaster（実部品・在庫マスタ）をCal固有実部品の主軸にする
- PartNameMaster（標準部品名マスタ）はメーカー横断で意味が安定する部品名に使い、対応が曖昧な部品を推測で統合しない
- クロノグラフ等、メーカーごとに機構・部品構成・名称が異なる領域ではメーカー/Cal固有部品名を許容する
- 日本語標準名が未確定でも、Cal・部品番号・メーカー原名等が分かれば登録できる方向で設計する
- メーカー原語名は保持し、日本語標準名と日本語仮訳を区別できる構造にする
- 部品表示は「日本語標準名 → 日本語仮訳 → メーカー英語名 → 最深カテゴリー名＋部品番号 → 部品番号」のfallbackを基本とする
- 発行済み帳票等はRepairLineItem側のsnapshotを保持し、後日の名称更新で過去表示を意図せず変更しない
- 内装部品はmovementCaliber（ムーブメントCal）中心
- UIではDB全体の部品を一括表示せず、最初にmovementCaliberで絞り、そのCalに存在するカテゴリー・機能・部品だけを通常候補に出す
- 候補数が多いカテゴリは「Cal → カテゴリ → 必要なら機能グループ → 部品」のdrill-down（段階絞り込み）を使う
- 部品名はメーカー固有を許容する一方、カテゴリーは機能ベースで可能な範囲を共通化し、UIの共通軸にする
- クロノグラフの分類候補として、秒クロノグラフ、分積算、時積算、発停・クラッチ、作動・制御、復針、受け・保持、その他を基本とする
- 1部品が複数機能にまたがる場合は、主カテゴリー + 機能タグ方式を候補として検討する
- 新規Calではメーカー解説書・部品表・展開図を根拠に部品番号、メーカー原名、日本語名/仮訳、カテゴリー候補を作成する
- 当面は「カタリが資料解析 → ヨシダ確認 → CodexでDB追加」の人間確認付き運用でCal別部品マスタを育てる
- 将来的なアプリ内AI自動解析は実例と費用対効果が十分に蓄積してから検討する
- baseMovementCaliber（ベースCal）がある場合は属性・部品候補・資料の継承/fallback条件を明示的に設計する
- Calごとに対応する解説書（Technical Document）を登録し、修理画面等から「解説書」ボタンで閲覧できるようにする
- 1資料が複数Calを対象にする場合、1Calに複数資料がある場合の両方を扱える構造にする
- 解説書の保存先はGoogle Drive等を含め要検討とし、DBを特定ストレージへ固定しない
- 将来的には解説書の部品表ページ・展開図ページ等を直接開ける余地を残す
- 解説書を保有していないCalの扱いは別途業務ルールを確定する。資料未登録表示、暫定部品登録、baseCal資料参照、代替資料登録等を検討対象とする
- 新規Cal登録時に部品カテゴリを毎回直接一括選択する運用を主方式にしない
- movementCaliberには、機械式/クォーツ、自動巻/手巻、日付、曜日、クロノグラフ、GMT、アラーム等のムーブメント属性を持たせる方向で設計する
- ムーブメント属性から利用可能な内装部品カテゴリ・機能候補を自動導出し、必要な場合のみCal固有override（例外設定）で追加/除外できる構造を目指す
- 外装部品はbrandId（ブランドID）/ modelId（モデルID）/ Ref（時計Ref）/ 部品Ref中心
- 外装部品も新規モデル/Ref登録時にカテゴリを毎回直接一括選択する方式を主方式にせず、時計属性・外装属性から候補カテゴリを自動導出する方向で設計する
- 時計全体の属性とムーブメント属性は混同しない
- external_labor（外装技術料）ではPartsMaster（実部品・在庫マスタ）を使わない
- part_external（外装部品行）ではPartsMaster（実部品・在庫マスタ）を使う
- 検索ワード生成はPartNameMaster.nameEnだけに依存せず、Cal、部品番号、メーカー原名、多言語名称、仕入先別ルールを利用する

### 作業順

1. 内装部品マスタ / Cal連動drill-down / 多言語名称の設計
2. TechnicalDocumentとCalの紐付け・解説書閲覧設計
3. 解説書未保有Calの業務ルール確定
4. 外装部品マスタ
5. 部品検索ワード生成修正
6. 複数サイト検索
7. 通貨変換
8. 検索結果の価格クリック挿入
9. 発注管理連携

### 完了条件

- 内装部品をCal中心に検索できる
- 内装部品選択でCalに存在しないカテゴリ・機能・部品が通常候補に混在しない
- 日本語標準名が未確定のメーカー固有部品も、メーカー原名・部品番号等で登録・識別できる
- 部品名fallbackがUIと帳票系で一貫したルールとして利用できる
- 新Calをメーカー資料から段階的に追加できる
- カテゴリーがメーカー固有名に依存せず、実用的なdrill-down軸として機能する
- 既知Calでは登録済み属性・部品候補を再利用できる
- Calに対応する解説書をアプリから開ける
- 1Cal複数資料 / 1資料複数Calを扱える
- 解説書未保有Calの業務ルールが明確になっている
- 外装部品をブランド/モデル/Ref/部品Ref中心に検索できる
- 新規モデル/Refでは時計・外装属性から外装部品カテゴリ候補を自動構成できる
- 複数サイト検索用の検索ワードが時計部品検索の実務に合う
- 検索結果の通貨を換算できる
- 部品価格をクリック操作で明細へ反映できる
- 発注が必要な部品を発注管理へ連携できる

## Phase 3: 現場運用・QRタグ

### 目的

時計1本ごとの現物とアプリ上の案件を素早く対応付ける。

### 対象

- 案件ごとのQRコード生成
- 小型タグ印刷
- 時計収納袋へのタグ同梱
- コードリーダー読み取り
- 案件詳細画面への遷移

### 方針

- 時計1本につき1枚の小型QRタグを作る
- QRタグは時計の収納袋に同梱する
- コードリーダーで読み取ると管理画面の案件詳細へ遷移する
- 管理画面の認証方針を壊さない

### 作業順

1. QRコードの識別単位とURL設計
2. 案件ごとのQRコード生成
3. QRコード表示
4. 小型タグ印刷レイアウト
5. コードリーダー読み取りから案件詳細画面への遷移確認

### 完了条件

- 時計1本につき1枚の小型QRタグを印刷できる
- QRタグを時計収納袋へ同梱できる
- QRをコードリーダーで読み取ると該当案件詳細画面を開ける
- 管理画面の認証方針を壊さない

## Phase 4: 作業可能判定・優先順位・スケジュール

### 目的

現在の修理品の中から今作業できるものを自動で特定し、優先順位を決め、作業スケジュール案を作る。

### 対象

- Repair（修理案件）
- RepairLineItem（修理明細）
- OrderRequest（発注依頼）
- status（案件ステータス）
- scheduledDate（予定日）
- estimatedWorkMinutes（見積作業時間）
- priorityScore（優先度スコア）
- 今日の作業ボード

### 方針

- まず作業可能判定を作る
- 作業できない案件は停止理由を明示する
- 優先順位ロジックは時計修理実務に合わせてユーザーと設計する
- 優先順位の根拠を確認できるようにする
- 完全自動で作業順を確定せず、人間が最終判断できる設計にする
- 作業可能判定と優先順位が安定してから自動スケジュール案を作る

### 優先順位ロジックの設計候補

以下は未確定の検討対象であり、実装前に業務ルールを確定する。

- 納期
- 受付日
- 長期滞留期間
- 見積承認状態
- 必要部品の準備状態
- 発注待ち状態
- 作業中断案件の再開可否
- 想定作業時間
- B2B/B2C
- 取引先または顧客ごとの優先条件
- 同一工程をまとめて行う効率

### 作業順

1. 作業可能条件の業務定義
2. 作業停止理由の業務定義
3. 作業可能判定
4. 停止理由表示
5. 優先順位ロジック設計
6. 優先順位表示
7. 今日の作業ボード
8. 作業時間情報の設計
9. 自動スケジュール案作成

### 完了条件

- 今作業できる案件が一覧で分かる
- 作業できない案件は理由が分かる
- 優先順位の根拠が分かる
- 今日やるべき作業候補を確認できる
- 現在の案件状態から作業スケジュール案を作れる

## Phase 5: 事例公開

### 目的

修理案件から公開事例を作成し、WEBサイトやInstagramへ活用できるようにする。

### 対象

- PublicCase（公開事例）
- WorkItem（公開作業項目）
- PartItem（公開部品項目）
- Image（公開画像）
- FMP過去修理データ
- WEB_APP案件
- WEB事例ページ
- Instagram投稿

### 方針

- 事例公開に合わせて業務アプリ設計を歪めない
- RepairLineItem（修理明細）の構造化データからPublicCase（公開事例）を作る
- B2BとB2Cで表示内容を分ける
- B2Cは価格非表示
- B2Bは条件を満たす場合のみ価格表示
- 公開前に人間が確認する

### 作業順

1. 現行RepairLineItem（修理明細）からPublicCase（公開事例）への接続確認
2. FMP過去修理データ移行資産の再確認
3. B2B/B2C表示分離確認
4. 投稿候補抽出
5. WEB事例出力
6. Instagram投稿用テキスト生成
7. 画像選定補助

### 完了条件

- 案件から公開事例を作れる
- FMP過去修理データを既存調査結果に沿って活用できる
- B2B/B2C表示ルールを守れる
- WEB事例とInstagram投稿に使える
- 公開前チェックができる

## 常時守る全体方針

- 現在Task対象外を変更しない
- 帳票/PDF/LINE/共有ページ/PublicCase（公開事例）は対象Taskでない限り触らない
- 内装/外装を混ぜない
- 作業マスタと部品マスタを混同しない
- メーカー資料の裏付けがない部品名を推測でメーカー横断統合しない
- Calに存在しない内装部品を通常候補へ混在させない
- RepairWorkAction（処置マスタ）を推測で追加しない
- RepairWorkCategory（作業カテゴリ）を推測で追加しない
- customerType（顧客区分）はbusiness（B2B）またはindividual（B2C）のみ
- customerType=nullの新規データを作らない
